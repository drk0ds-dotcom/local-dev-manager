# تصميم نشر Local Dev Manager على GitHub

**التاريخ:** 2026-09-28  
**الحالة:** بانتظار مراجعة المستخدم  
**المالك العام للمستودع:** `drk0ds-dotcom`  
**صاحب حقوق النشر:** `Burayk`  
**الترخيص:** MIT

## 1. الهدف

تجهيز مشروع **Local Dev Manager** الحالي للنشر العام في مستودع GitHub جديد باسم:

```text
drk0ds-dotcom/local-dev-manager
```

يجب أن يفهم الزائر خلال دقيقة واحدة أن المشروع تطبيق سطح مكتب لإضافة مشاريع Node.js المحلية وتشغيلها وإيقافها وإعادة تشغيلها ومتابعة مخرجاتها ومنافذها من واجهة واحدة. يجب أن يستطيع مستخدم Windows تنزيل المثبّت وتجربة التطبيق دون الحاجة إلى بناء المصدر، وأن يستطيع المطور بناء المشروع وتشغيل اختباراته من تعليمات واضحة.

## 2. الحدود الصارمة

- يُنشأ مستودع جديد فقط باسم `local-dev-manager`.
- لا يُحذف أو يُعدّل أو يُؤرشف أو يُعاد تسمية أي مستودع سابق في حساب GitHub، سواء كان عامًا أو خاصًا.
- إذا كان الاسم المستهدف مستخدمًا مسبقًا، يتوقف التنفيذ ويُبلّغ المستخدم دون لمس المستودع الموجود.
- لا تُرفع `node_modules/` أو مخرجات البناء الكاملة أو بيانات المستخدم المحلية.
- لا تُنشر أسرار أو رموز وصول أو شهادات توقيع أو كلمات مرور.
- لا يُدّعى دعم منصة أو ميزة لم تُثبت من الكود أو الاختبارات الحالية.
- لا يُحذف أي ملف محلي مستبعد من النشر؛ يكفي تجاهله في Git.

## 4. تموضع المنتج

Local Dev Manager ليس بديلًا لخوادم الإنتاج مثل PM2، وليس IDE كاملًا. قيمته الأساسية هي إدارة جلسات التطوير المحلية لمشاريع Node.js من واجهة سطح مكتب واحدة، مع التركيز على:

- تشغيل المشروع وإيقافه وإعادة تشغيله.
- اكتشاف مدير الحزم وسكربت التشغيل والإطار المستخدم.
- تثبيت الحزم تلقائيًا عند غياب `node_modules`.
- تخصيص منفذ متاح ومتابعة المنفذ الفعلي.
- عرض السجلات والبحث فيها ومسحها وتصديرها.
- فتح المشروع في المتصفح أو VS Code أو مستكشف الملفات.
- التشغيل التلقائي وإعادة التشغيل المقيدة عند التعطل.
- عرض حالة التشغيل ومدة التشغيل واستهلاك الموارد.
- واجهة عربية وإنجليزية داخل التطبيق.

اللغة الصينية ستكون لغة توثيق في GitHub ضمن هذا الإصدار، وليست لغة واجهة للتطبيق. يجب توضيح هذا الفرق حتى لا يفهم الزائر أن الواجهة الصينية موجودة فعليًا.

## 5. الجمهور المستهدف

- مطورو Node.js الذين يديرون عدة مشاريع محلية في الوقت نفسه.
- المطورون الذين يريدون تقليل عدد نوافذ Terminal المفتوحة.
- المستخدمون الذين يفضلون واجهة رسومية لإدارة خوادم التطوير والمنافذ والسجلات.
- المساهمون الراغبون في فهم تطبيق Electron صغير ومباشر.

## 7. سياسة الملفات

### ملفات تُنشر

- المصدر الفعلي للتطبيق.
- الاختبارات الآلية.
- ملفات إدارة الحزم وقفل الاعتمادات.
- الأيقونة الرسمية المستخدمة في البناء: `assets/icon.png`.
- مشغلات التطوير العامة على Windows (`.bat` و`.vbs`) بعد التحقق من خلوها من المسارات الثابتة.
- ملفات التوثيق والمجتمع والأمان.
- صور واجهة منقحة ومقصودة للتوثيق.

### ملفات لا تُنشر في تاريخ Git

- `node_modules/`؛ لأنها اعتماد قابل للاستعادة بـ `npm ci` ويبلغ حجمها المحلي حاليًا قرابة 360 MB.
- `dist/`؛ لأنها مخرجات بناء تبلغ قرابة 367 MB، وتوضع الأصول اللازمة منها في GitHub Release.
- `projects.json`؛ لأنه ملف بيانات مستخدم محلي.
- `builder-debug.yml` والسجلات والملفات المؤقتة.
- ملفات `.env*` والمفاتيح والشهادات وملفات التوقيع.
- `vibe_images/` وصور الأيقونات الاحتياطية أو المكررة غير المستخدمة في البناء.

تعتمد الحماية على `.gitignore` موسع، ثم فحص قائمة الملفات المرحلية قبل أول Commit وقبل Push.

## 9. الصور

تُستخدم الصور المرسلة بوصفها **Application Screenshots / Manual Validation**، ولا تُقدّم على أنها اختبارات آلية.

الصور المستهدفة:

- `docs/images/project-running.png`: الصورة الرئيسية لحالة تشغيل مشروع.
- `docs/images/empty-state.png`: توضح الشاشة الأولى قبل إضافة مشروع.
- `docs/images/arabic-interface.png`: توضح واجهة RTL العربية.

متطلبات المعالجة:

- إخفاء أو قص المسارات الشخصية مثل `C:\Users\<username>` عندما تسمح المعالجة بالحفاظ على دقة لقطة الشاشة.
- تجنب إبراز تحذير Next.js الخاص بالمشروع التجريبي باعتباره خطأ في Local Dev Manager.
- الحفاظ على صدق الواجهة وعدم إضافة وظائف غير موجودة.
- استخدام نص بديل واضح لكل صورة.
- عدم تكرار الصور داخل كل README؛ تشير الصفحات الثلاث إلى الملفات المشتركة نفسها.

تحديث بعد تسلم الصور 5–9: اختيرت اللقطات الأصلية 5 و7 و9. محاولة تنقيح آلي للمسار غيّرت تفاصيل أخرى في الواجهة، لذلك استُبعدت النتيجة للمحافظة على صدق العرض. تظهر أسماء ومسارات مشاريع تجريبية محلية في اللقطات المنشورة، ولا تحتوي على أسرار.

## 10. منصة الإصدار المدعومة

الإصدار الثنائي الأول المعلن هو **Windows x64**. توجد أجزاء من منطق العمليات تراعي POSIX، لكن لا يوجد في المشروع الحالي دليل اختبار وتغليف مكافئ لـ macOS أو Linux؛ لذلك لا يوصف دعمهما بأنه رسمي في الإصدار `v1.0.0`.

يمكن الإشارة إلى أن البناء من المصدر على منصات أخرى غير موثق أو غير متحقق منه، دون وعود إضافية.

## 11. Windows SmartScreen وتوقيع الكود

تتضمن الصفحات الثلاث قسمًا واضحًا يشرح:

- قد يظهر Windows SmartScreen لأن الإصدار الحالي لا يحمل شهادة Code Signing موثوقة واسعة السمعة.
- ظهور التحذير ليس وحده دليلًا على أن الملف ضار.
- يجب تنزيل المثبّت من GitHub Release الرسمي فقط.
- يجب مقارنة `SHA-256` بالقيمة المنشورة قبل التشغيل عند الحاجة إلى تحقق إضافي.
- خطوات SmartScreen تُشرح بوضوح دون الادعاء بأن التطبيق موقّع أو موثوق من Microsoft.

## 12. الإصدار `v1.0.0`

ينشأ GitHub Release عام بعلامة `v1.0.0` بعد نجاح التحقق. يتضمن:

```text
Local Dev Manager Setup 1.0.0.exe
Local Dev Manager Setup 1.0.0.exe.blockmap
latest.yml
SHA256SUMS.txt
```

- المثبّت هو ملف التنزيل الرئيسي للمستخدم.
- `latest.yml` وملف `.blockmap` مطلوبان لمسار `electron-updater` الموجود فعليًا في `main.js`.
- `SHA256SUMS.txt` يحتوي قيمة SHA-256 للمثبّت وبقية أصول الإصدار المناسبة.
- لا يُرفع `builder-debug.yml` ولا مجلد `win-unpacked`.
- تتضمن Release Notes ملخصًا قصيرًا بالإنجليزية والعربية والصينية.
- لا يُستخدم خيار حذف Release أو إعادة إنشاء المستودع كوسيلة لمعالجة فشل الرفع؛ تُستكمل الأصول الناقصة أو يُبلغ المستخدم.

## 13. إعدادات التطبيق المرتبطة بـ GitHub

يُستبدل placeholder الحالي:

```text
YOUR_GITHUB_USERNAME
```

بالمالك المعتمد:

```text
drk0ds-dotcom
```

وتضاف بيانات `repository`, و`homepage`, و`bugs`, و`author`, و`license` المناسبة إلى `package.json`. يجب أن تكون روابط التحديث والإصدار متوافقة مع المستودع العام الجديد.

## 14. GitHub Actions

يضاف Workflow للتحقق فقط، وليس للنشر التلقائي في المرحلة الأولى. يعمل على Windows ويشغّل على الأقل:

```text
npm ci
npm test
node --check للملفات البرمجية الأساسية والاختبارات
```

لا يحمل Workflow شهادة توقيع ولا GitHub Personal Access Token. يعتمد على صلاحيات قراءة محدودة ما لم تتطلب خطوة موثقة غير ذلك. نشر `v1.0.0` الأول يتم بعد التحقق المحلي وبإجراء منفصل ومقصود.

## 15. ملفات المجتمع

- `CONTRIBUTING.md`: إعداد بيئة التطوير، أسلوب الإبلاغ، الاختبارات المطلوبة، وعدم إدراج الملفات المولدة.
- `SECURITY.md`: الإبلاغ الخاص عن الثغرات وعدم نشر التفاصيل الحساسة في Issue عامة.
- `CODE_OF_CONDUCT.md`: قواعد المشاركة المجتمعية.
- Issue templates منفصلة للأخطاء وطلبات الميزات.
- `LICENSE`: نص MIT القياسي باسم Burayk وسنة 2026.

## 16. التحقق قبل النشر

يجب تنفيذ الأدلة التالية من حالة نظيفة قدر الإمكان:

- نجاح مجموعة الاختبارات كاملة؛ العدد الحالي المتوقع 11 اختبارًا.
- نجاح فحص صياغة ملفات JavaScript الأساسية والاختبارات.
- نجاح بناء Windows عبر `npm run dist`.
- فحص `app.asar` للتأكد من وجود الاعتمادات الإنتاجية المطلوبة.
- فحص المستودع المراد رفعه بحثًا عن الأسرار والمسارات الشخصية غير المقصودة.
- فحص الروابط النسبية بين ملفات README الثلاثة.
- التأكد من أن الصور المشار إليها موجودة وتُعرض.
- حساب SHA-256 من ملف المثبّت النهائي نفسه.
- مراجعة قائمة Git المرحلية والتأكد من غياب `node_modules`, و`dist`, و`projects.json`.

## 17. تسلسل النشر الآمن

1. تجهيز الملفات والتوثيق محليًا.
2. تشغيل الاختبارات والبناء والفحوصات.
3. مراجعة الملفات التي سيدخلها Git فقط.
4. التأكد عبر GitHub API/CLI أن `drk0ds-dotcom/local-dev-manager` غير موجود.
5. إنشاء المستودع العام الجديد فقط.
6. دفع الفرع الافتراضي.
7. التحقق من عرض README واللغات وCI في GitHub.
8. إنشاء Tag وRelease `v1.0.0` ورفع الأصول الأربعة.
9. التحقق من روابط التنزيل وقيمة SHA-256 وبيانات التحديث.

عند فشل أي خطوة لا تُستخدم عمليات حذف أو إعادة إنشاء. يُحافظ على الحالة القابلة للإصلاح ويتوقف التنفيذ عند الحاجة إلى قرار المستخدم.

## 18. معايير الاكتمال

يُعد النشر مكتملًا فقط عندما:

- يكون المستودع العام الجديد ظاهرًا تحت الحساب المتفق عليه.
- لا يكون أي مستودع سابق قد عُدل.
- تعرض الصفحة الافتراضية وصفًا إنجليزيًا واضحًا وروابط عربية وصينية تعمل.
- تكون الميزات المعلنة قابلة للإثبات من الكود.
- ينجح CI والاختبارات المحلية.
- يكون `v1.0.0` قابلًا للتنزيل مع checksum صحيح.
- يكون SmartScreen موثقًا بوضوح.
- لا توجد أسرار أو بيانات مستخدم أو مكتبات مثبتة أو مخرجات بناء كاملة في تاريخ Git.

## 19. مراجع أسلوب التوثيق

استُخدمت هذه المستودعات كمراجع للأسلوب والبنية، دون نسخ نصوصها أو ادعاء تشابه وظائفها:

- [OpenCodex](https://github.com/lidge-jun/opencodex): لغة تعريف مباشرة، Quick Start، التنزيلات، وتعدد اللغات.
- [Microsoft PowerToys](https://github.com/microsoft/PowerToys): وصف واضح، تنزيل Windows، وفصل التثبيت عن التفاصيل.
- [GitButler](https://github.com/gitbutlerapp/gitbutler): عرض القيمة، الصور، والميزات الأساسية.
- [Beekeeper Studio](https://github.com/beekeeper-studio/beekeeper-studio): شريط اختيار اللغات والتوثيق متعدد اللغات.
- [PM2](https://github.com/Unitech/pm2): وضوح مفاهيم إدارة العمليات وأوامر التشغيل.

الاختيار المتعمد هو README احترافي ومركز، لا صفحة تسويقية مبالغًا فيها ولا سجل تطوير طويل في الواجهة الأولى.
